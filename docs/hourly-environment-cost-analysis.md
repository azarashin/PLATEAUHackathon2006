# 時間別環境コストの解析・検証・可視化

Issue #8で、道路エッジごとの08:00〜17:00（JST）の時間別環境コストを、再実行可能な解析成果物として扱えるようにした。本資料は計算式、欠測の扱い、キャッシュ、進捗・中断、検証、Unityでの可視化を定義する。

## 値の定義

道路エッジには、OSM形状から求めた`lengthMeters`、歩行速度1.4 m/sで求めた`walkingSeconds`、道路面上のサンプル数を記録する。各時刻には次を記録する。

| 項目 | 単位・範囲 | 定義 |
|---|---|---|
| `shadeRatio` | 0〜1 | 有効な道路面サンプルのうち、建物LOD1が太陽光を遮るサンプルの割合 |
| `solarExposureSeconds` | 秒 | そのエッジを歩く間に日向へ曝露される推定時間 |
| `sunElevationDegrees` | 度 | 対象日時・中心座標における太陽高度 |
| `timestamp` | ISO 8601 | 地域設定のタイムゾーンを含む時刻。市ヶ谷は`+09:00` |
| `status` | 文字列 | `available`、`partial`、`missing`のいずれか |
| `exclusionReason` | 文字列または`null` | 一部または全部を計算できない理由 |

日射曝露時間は次の固定式で計算する。

```text
solarExposureSeconds = walkingSeconds * (1 - shadeRatio)
```

JSONには丸めず倍精度の値を保存し、検証許容差を`1e-6`秒とする。UI表示時だけ、日陰率は小数2桁、秒は小数1桁など用途に応じて丸める。解析結果を入力とする経路コスト計算では保存値を使用する。

## 欠測と除外理由

全エッジ・全設定時刻を必ず出力する。計算できない組み合わせを配列から除外せず、理由を明示する。

| 条件 | `status` | `exclusionReason` | 値 |
|---|---|---|---|
| 全サンプルで道路面を取得 | `available` | `null` | 日陰率・日射曝露時間あり |
| 一部の道路面を取得できない | `partial` | `some-road-samples-not-found` | 有効サンプルによる値あり |
| 有効な道路面がない | `missing` | `road-surface-not-found` | 両方`null` |
| 太陽高度が0度以下 | `missing` | `sun-below-horizon` | 両方`null` |

`validSampleCount + noGroundSampleCount = sampleCount`もエッジごとに検証する。時刻配列の不足、順序違い、重複エッジID、範囲外の日陰率、上式との差異が1件でもあれば最終出力を確定しない。

## 実行状態、中断、失敗

`stateOutputPath`は実行開始時に`running`となり、フェーズ、処理済みエッジ数、処理済み時刻数、更新時刻を記録する。終了状態は次のとおりである。

- `completed`: 全エッジ・全時刻を検証し、結果JSONを原子的に置換済み
- `failed`: 例外により失敗。メッセージを状態ファイルへ記録
- `cancelled`: 利用者または中断要求ファイルにより中断

結果、状態、キャッシュは同じディレクトリの`.partial`へ書き、フラッシュ後に置換する。中断・失敗時は未完成の`.partial`だけを除去し、以前の完了結果は維持する。そのため不完全な結果を`completed`として扱わない。

Unity Editorでは進捗ダイアログの「Cancel」、バッチ実行では設定の`cancellationRequestPath`にファイルを作ることで中断する。バッチの終了コードは成功`0`、失敗`1`、中断`2`である。

## 時刻別キャッシュと再現性

解析キーはSHA-256で生成する。キーには解析条件、メッシュ対応表の内容、OSM入力の内容、対象CityGMLファイルの相対パス・サイズ・更新時刻を含める。いずれかが変わると別のキーになる。

キャッシュは次の単位に分ける。

- `<analysis-key>-edges.json`: 道路形状、歩行時間、道路面サンプル集計
- `<analysis-key>-hour-HH.json`: 1時刻分の日陰率と日射曝露時間

すべての時刻が存在すればCityGMLのインポートを省略する。一部だけ存在する場合は不足時刻だけを計算し、結果を全時刻へ再構成する。`-forceRecalculate`を付けると読取りキャッシュを無視して全時刻を再計算し、新しいキャッシュを書き出す。

`generatedAt`を除いた安定部分から`resultFingerprintSha256`を計算する。同じ入力・設定の初回実行とキャッシュ再実行でこの値が一致することを再現性の判定に使う。

## Unityでの日陰ヒートマップ確認

1. `tools/plateau-environment-cost-analyzer`をUnity Editorで開く。
2. `PLATEAU > Environment Cost > Hourly Heatmap`を開く。
3. `completed`の環境コストJSONを選択して`Load`を押す。
4. `Hour`で08〜17時を切り替え、Sceneビューを確認する。

日陰率0を橙、1を緑、中間を補間色で描く。`missing`は灰色、`partial`は透明度を下げる。選択時刻を変えるたびにSceneビューを再描画し、状態別エッジ件数も表示する。描画負荷を抑えるため表示上限を変更できる。これは解析値の検査用であり、ブラウザ向け地図レイヤーはIssue #9以降で軽量化する。

## 市ヶ谷実データでの確認結果

2026-08-23に、市ヶ谷中心・半径4 km、2025-08-01、08〜17時、25 m間隔、ノードID付きOSMスナップショットで実行した。

| 指標 | 結果 |
|---|---:|
| 道路エッジ | 130,521 |
| 時刻 | 10 |
| サンプル | 305,118 |
| 有効サンプル | 229,652 |
| 道路面欠測サンプル | 75,466 |
| 各時刻の`available` | 92,135エッジ |
| 各時刻の`partial` | 7,539エッジ |
| 各時刻の`missing` | 30,847エッジ |
| 結果JSON | 296,190,573 bytes（約282.47 MiB） |
| キャッシュ | 11ファイル、344,878,624 bytes（約328.90 MiB） |
| 解析キー | `909c3245f6565cd30c37a9faead4245fb6e5f294d2ff802c25278a8e2d6086c7` |
| 結果フィンガープリント | `cc078d7674acb76119e8bfd0dc8f39729d5de61f382c97a5d1a65363a85f75f5` |

全計算・キャッシュ生成を含む初回は608.95秒、キャッシュ再実行は190.60秒だった。キャッシュ再実行は10/10時刻がヒットし、CityGMLインポートを省略した。両実行の結果フィンガープリントは完全一致した。初回の外部観測ピークワーキングセットは約12.0 GiB、キャッシュ再実行は約2.0 GiBだった。初回値には進捗ファイル更新の調整前の時間を含むため、性能回帰の基準値にはせず、代表規模と再現性の証跡として扱う。

次のコマンドで実出力を検証し、全130,521エッジ×10時刻について成功した。

```powershell
node --max-old-space-size=4096 tools/hourly-environment-cost/validate-hourly-output.mjs `
  data/generated/ichigaya-venue-environment-cost.json
```

約282 MiBの解析JSONはブラウザへ直接配信しない。経路探索向けの結合・範囲抽出・配信用軽量化はIssue #9の対象とする。
